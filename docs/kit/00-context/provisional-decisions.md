# Provisional Decisions

The kit had to decide these to be buildable. **None is confirmed by the team.** Each has the alternative that would be used instead. Before building the part a decision affects, the team marks it Confirmed or Changed. A builder must not treat a Provisional row as settled.

v3 changed PD-1, PD-3, PD-4, PD-10, PD-12, PD-14 and PD-15 for the browser-based IDE (R-16) and added PD-17 to PD-24. The fix-flow revision replaced PD-7 with PD-25 and added PD-26 to PD-29.

| ID | Decision | Why | Alternative | Affects | Status |
| --- | --- | --- | --- | --- | --- |
| PD-1 | Reprise features live in a **built-in web extension** inside the fork (`extensions/reprise/`, `browser` entry point only), using only the public VS Code extension API. The fork itself changes only branding, gallery, web-build configuration and bundling. | Smallest fork diff; the web-worker extension host is what runs in the browser; the extension can be developed against any Code - OSS web build. | Modify the workbench core directly. | Everything | Provisional |
| PD-2 | Implementation language is TypeScript. | Code - OSS and its extension API are TypeScript. | — | Everything | Provisional |
| PD-3 | Fork from a pinned **stable release tag** of `microsoft/vscode`, recorded in `02-specs/ide-fork.md`, not from `main`. Only the **web** build target is produced. | Reproducible builds; R-16 makes the web target the product. | Track `main`; also produce desktop builds. | Fork | Provisional |
| PD-4 | Product name "Reprise IDE", short name "Reprise", application name `reprise`. The IDE is served at `https://OWNER.github.io/reprise-ide/ide/`. | Required rebranding (gate G-4); one Pages site for IDE and dashboard. | Another name; a separate repository or custom domain for the IDE. | Fork, hosting | Provisional |
| PD-5 | The Bug Reports view lists open issues with the label `bug` by default (configurable in `.reprise.yml`). | Keeps the list focused. | All open issues. | GitHub connection | Provisional |
| PD-6 | Acknowledging does not post anything to GitHub by itself (R-4 says it starts replication). Posting results as an issue comment is a setting, **off by default**. | R-4 chose "starts replicating" over "posts a comment". | Post a comment on acknowledge and on verdict. | GitHub connection | Provisional |
| PD-7 | Replaced by PD-25. | — | — | — | Superseded |
| PD-8 | Driver fallback tests are written in JavaScript using the WebdriverIO client against a local Appium 2 server, both started by the Reprise Runner. | One language for all fallback tests; free and open source. | Python Appium client, or per-platform native frameworks. | Test execution | Provisional |
| PD-9 | No driver fallback for Linux desktop apps in this version unless gate G-13 finds a maintained option; Linux uses the repository command only. | No official Appium Linux desktop driver was found (V-3). | A community driver found by G-13. | Test execution | Provisional |
| PD-10 | Any test not written by the user (stub- or AI-provided) is shown in a diff view and needs the user's explicit approval in the IDE before it is written to the folder, and the runner refuses test files it has not been told were approved (`local-runner.md`). | Local execution has no sandbox for native GUI apps. | Run automatically. | Security | Provisional |
| PD-11 | Stub fixtures live in the target repository under `.reprise/stubs/<issue-number>/`, read through the opened folder. | Visible, versioned, easy to prepare per demo bug. | Stored inside the IDE's own storage. | AI providers | Provisional |
| PD-12 | Issue records are stored on a `reprise-data` branch of each target repository, committed by the IDE through the GitHub REST Git Data API with the user's GitHub authorisation. | Zero cost; the dashboard can read public branches; no git binary in the browser. | A single central data repository. | Data, dashboard | Provisional |
| PD-13 | The dashboard is hosted with GitHub Pages from the `reprise-ide` repository at `https://OWNER.github.io/reprise-ide/` and aggregates the `reprise-data` branches of repositories listed in `dashboard/repos.json`. | One public URL for judges; the IDE sits beside it at `/ide/` (PD-4). | A separate dashboard repository. | Dashboard | Provisional |
| PD-14 | The CI executor uses a workflow file that the IDE proposes as a PR with the command "Reprise: Set Up CI Runs"; the IDE starts it with `workflow_dispatch` and reads results from a run artifact through the GitHub REST API. | Keeps target repos opt-in and explicit; works from the browser without a runner (subject to G-24). | Commit the workflow by hand. | Test execution | Provisional |
| PD-15 | Tests started by the Reprise Runner get the environment of the shell that started the runner, minus variables that hold credentials (see `02-specs/security.md`). | Local tests usually need the user's toolchain environment. | Empty environment plus an allow-list. | Security | Provisional |
| PD-16 | Verification runs are started from the IDE (command or button on a PR), not automatically by GitHub Actions on every push. | The IDE is the product; CI runs remain available as an executor. | Also run on every PR push. | Fix and verify | Provisional |
| PD-17 | Local test runs go through the **Reprise Runner**: a Node.js program in `reprise-ide/runner/`, started by the user with `node reprise-runner.mjs --root <repo folder>`, listening on `127.0.0.1` only, paired with one IDE tab by a one-time code, accepting only the run requests in `local-runner.md`. | A browser tab cannot start processes; R-7 requires runs on the user's machine and devices. | A native messaging host installed next to the browser; CI-only (drops the local part of R-7). | Test execution, security | Provisional |
| PD-18 | The runner reads commands **only** from `.reprise.yml` in its own `--root`; the IDE sends a platform, a mode, a test path and a run count, never a command string. | A compromised or misled tab cannot make the runner execute arbitrary commands. | The IDE sends the command. | Security | Provisional |
| PD-19 | Branches, commits and PRs are created through the GitHub REST API (Git Data API for blobs, trees, commits and refs) from file contents read through the opened folder. Reprise never changes the local folder's git state; the user's local checkout stays on whatever branch they had. | No git binary in the browser; keeps the GitHub token in the browser only. | Have the runner run `git` with the user's credentials. | GitHub connection, fix | Provisional |
| PD-20 | R-14 "installers on GitHub Releases" becomes: the IDE URL (no installation), plus `reprise-runner.mjs` and its SHA-256 on GitHub Releases. BUILDING.md covers building the web IDE and running it locally. | The IDE is a web page (R-16). **R-14 is a team answer, so the team must confirm this.** | Also build desktop installers from the same fork. | Release | Provisional |
| PD-21 | The extension gallery is **turned off** in the web build (no `extensionsGallery` in `product.json`). | Third-party extensions would run in the same browser origin as the GitHub token; nothing in the demo needs them. | Open VSX gallery as in v2 (V-2), limited to web extensions. | Fork, security | Provisional |
| PD-22 | Supported browsers: desktop Chrome and Microsoft Edge, at the versions recorded by gate G-20. Other Chromium browsers (Brave, Opera, Vivaldi, Arc) are "should work, not tested" unless G-20 tests them. | R-16 names Edge and Chrome-based browsers; the team can only test a few. | Test and list every Chromium browser. | Browser support | Provisional |
| PD-23 | GitHub sign-in in the browser uses a **fine-grained personal access token** entered by the user, limited to the target repositories, stored in the workbench's secret storage. Device flow is used only if gate G-22 shows it works from the browser without a server. | A zero-cost static site has no server to hold an OAuth client secret or proxy OAuth endpoints. | A free serverless proxy for the OAuth device flow (would need its own cost check). | GitHub connection, security | Provisional |
| PD-24 | The runner uses git only for read-only work: detecting the remote and `HEAD`, and creating temporary worktrees of base and head refs for verification in its own cache folder, using the user's existing git credentials. It never pushes. | Verification needs base and head checked out; the browser cannot do that on disk. | The IDE writes both versions through the File System Access API into a scratch folder the user picks. | Fix and verify | Provisional |
| PD-25 | Trials are an adjustable policy: `min` 10, `max` 20, `limit` 100, optional `max_minutes`; stop at `min` if every run failed; set in `.reprise.yml` (per platform too) and changeable per replication in the IDE (`statistics.md` §2a). A number means a fixed count. | 10 matches common flaky-test practice (Google 5–10 runs, iDFlakies 10); 20 is the concept paper's count and bounds "never failed" under 14%; deterministic bugs finish in half the time. | Fixed 20 (the concept paper, and v2's PD-7). | Replication, statistics | Provisional |
| PD-26 | Fixes are proposed as **3 candidates per round**, filtered by quick checks (reproduction test and suite) and ranked; at most 3 rounds (`fix-and-verify.md` §4). | Parallel candidates filtered by tests work better than retrying one (Agentless); 3 keeps device run time manageable. | 1 candidate per round (v2). | Fix | Provisional |
| PD-27 | Candidates run on CI when it is configured; otherwise locally in runner worktrees after one batch approval. They never run in the opened folder. | Candidates are code nobody has reviewed yet (PD-10); CI runners are ephemeral and run in parallel. | Approve each candidate separately; local only. | Fix, security | Provisional |
| PD-28 | The fix PR is opened as a **draft** as soon as a candidate is applied, with a checklist the IDE updates; the user marks it ready after `FIX_VERIFIED`. | Visible progress and a place for review comments from the start (GitHub Copilot coding agent). | Open a normal PR after verification (v2). | Fix, GitHub connection | Provisional |
| PD-29 | A **self-review** stage (`review`) runs after verification, plus the repository's lint command if configured; high-severity findings offer a new round. | A separate reviewer catches problems tests miss (CodeRabbit). | No self-review. | Fix, providers | Provisional |
